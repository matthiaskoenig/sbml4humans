# Release notes for sbml4humans 0.13.0

A document which crashes libsbml now costs an error message instead of the service: the report of every document a request brings is built in a process of its own, bounded in time and in memory, so that a crash of libsbml is the answer to one request and no other reader loses their report.

## Reports which cannot take the server down
- the report of a file, a url, pasted content or an upload of another tool is built in a child process of the backend, as its validation already was: a document which ends that process, which a document libsbml reads without a single error can do, is reported as "The document could not be reported: the process which read it ended unexpectedly", and the server answers the next report as though nothing had happened ([#132](https://github.com/matthiaskoenig/sbml4humans/issues/132))
- the guards which answered the shapes found before this release, each written against the one shape which had been measured ([#127](https://github.com/matthiaskoenig/sbml4humans/issues/127), [#130](https://github.com/matthiaskoenig/sbml4humans/issues/130) and [#131](https://github.com/matthiaskoenig/sbml4humans/issues/131), below), stay where they are with their tests and are defence in depth now that the process boundary answers the class, a document which ends the process which reads it, and not only the shapes someone looked for
- a report may take 180 seconds and 4 GiB of memory; one which takes longer or needs more is stopped and says which of the two bounds it met, instead of holding the server for as long as libsbml wants
- a report asked for while the server is building others waits for a free process, at most the 180 seconds a report may take, and one asked for beyond the few which may wait is answered at once with the message to try again in a moment, so that a few large documents cannot keep the machine busy for everyone
- the reports and the validations of a server are admitted apart from each other: a server busy with reports still validates, and a server busy with validations still reports
- a report whose reader closed the page or pressed stop is cancelled, its process ends at once and the place it held is free for the next reader
- a document which expands by its comp submodels to more than 10,000 elements, the bound its validation already had, keeps its report and loses its equations: flattening such a model needs more memory than any report may use, a few kilobytes of submodels are enough for it, and the view of the equations now says that they were not built and how far the model expands, in place of a report which is refused
- the downloads of the differential equations of a document (`/api/ode/...`) read that document in a process of their own as well, and a download which was stopped says that it was the ODE system and never a report
- nothing else changed: the reports of the examples and of `sbml4humans.show`, which reads a file of your own machine, are built as before, the data of a report, its api and the application are as they were, and no schema changed

## The math and the units of a report
- a math the backend cannot typeset is shown as its formula in text, and the report of its document is no longer lost with it ([#128](https://github.com/matthiaskoenig/sbml4humans/issues/128))
- a kinetic law of a Level 1 document whose formula is `lambda()`, which ends the MathML writer of libsbml with a segmentation fault, is refused before that writer sees it; reported upstream as [sbmlteam/libsbml#521](https://github.com/sbmlteam/libsbml/issues/521) ([#127](https://github.com/matthiaskoenig/sbml4humans/issues/127))
- a model whose math is too deep for the unit inference of libsbml, which a wide sum is because libsbml reads it as a deeply nested tree, or whose function definitions call each other in a cycle, is reported without the derived units of its elements and with one warning which names the model, instead of ending the process ([#130](https://github.com/matthiaskoenig/sbml4humans/issues/130))
- the cache of the typeset math of a worker is bounded in bytes, 32 MiB, and no longer in entries, since one math is as large as its file allows ([#131](https://github.com/matthiaskoenig/sbml4humans/issues/131))

## Deployment
- `SBML4HUMANS_REPORTS` is the number of reports a server builds at a time, 1 in production, and the ODE downloads of a request share those children; without the variable the backend builds as many reports at a time as half the cpus it may run on, and twice as many requests wait for their turn before one is answered as busy
- a report child may use up to 4 GiB of memory, so a host pays 1 x 4 GiB for the reports on top of the 2 x 2 GiB of the validations, 8 GiB of children with the backend on top of them: production builds one report at a time until the memory of its host is measured, the arithmetic is in `deploy.md` and in the comment of `docker-compose-production.yml`, read it before raising either number
- the proxy of sbml4humans.de limits the report requests of one address as it limits the validations, 2 open at a time and 20 a minute, so that one reader cannot hold every report of the server; `nginx/` is copied to the proxy by hand, so this limit reaches the site with that copy and not with the deploy of the containers
