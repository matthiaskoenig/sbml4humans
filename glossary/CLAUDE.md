# CLAUDE.md - glossary

The glossary, its generator in `backend/sbml4humans/` and its consumers.

**`glossary/*.toml`, `glossary.py`, `glossaryrules.py` - the explanations.** The glossary in the repository root (`core.toml` the SBML core types and their attributes, `packages.toml` the comp, fbc and distrib types, `report.toml` the link kinds and the concepts the report adds) is the single source of every explanation: an entry has a `label`, a one sentence `summary` and a markdown `description`, and nothing is explained or named anywhere else. The `label` of a type is its class name (`FunctionDefinition`), the `label` of an attribute which cites a `spec` is its name in the specification (`initialConcentration`, `fbc:charge` for an attribute a package adds to a core type), the `label` of a link kind is its key, and only what the report adds is labelled in plain words (`derived units`); `--check` enforces this. An attribute which cites a `spec` also states `required`, optionally a `default` (one clause, only next to `required = false`) and `rules`, the numbers of the validation rules of libsbml which concern it; a type states the rules about the element as a whole, and `[datatypes.*]` explains every `type` an attribute names which is no type of the glossary (the data types of the specifications and the kinds of value the report adds), with `values` for an enumeration. `glossaryrules.resolve_rule(code)` is where a rule becomes text: the number gives the package (core below 1,000,000, a package by the error id offset of its libsbml extension), a core rule resolves through `SBMLError` in the newest version which has it and a rule of a package through the error table of its extension, and the trailing `Reference:` of the message becomes the `section`. Nothing of a rule is ever written by hand. The frontend states no names of its own: the type bar, the table headings and the inspector header show the type, and the column headers (`report/columns/`, a column states no header), the rows of the inspector (`AttributeRow` by `type` and `field`), the nested tables and the link groups take their label from the glossary; the only words the frontend owns are the chrome of the help dialog in `components/help/words.ts` and in the components themselves. `sbml4humans.glossary` generates the three consumers from it: `frontend/src/data/glossary.json`, which `frontend/src/report/glossary.ts` turns into the names and the tooltips of the columns, attributes, type marks and link groups and into the links into the reference and into the key of every entry, `frontend/src/data/glossary-details.json`, the description and the technical detail of every entry for the help dialog, keyed by `types/Species`, `types/Species/initialAmount`, `links/compartment`, `concepts/pk` or `datatypes/SIdRef`, with the links of a description rewritten to `glossary:<key>` or to an absolute url of the site, and `docs/reference/*.md`, the reference pages, whose attribute table carries the column `required`, whose attributes state their default and list their rules, and among which `datatypes.md` explains the data types. Run `uv run python -m sbml4humans.glossary` after a change of the glossary or of the report model and commit all three outputs; `--check` fails when a generated file is stale, when a type or a field of the report model has no entry, when a glossary type is not a type of the report, when an attribute of a specification does not state whether it is required, when an attribute the report adds states `required`, when a rule is unknown to libsbml, is listed twice or belongs to a foreign package, when a `type` resolves to neither a data type nor a type of the glossary, when a data type is unused, when a link of a description does not resolve or when a page references a missing image.
